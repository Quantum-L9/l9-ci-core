# Nightly findings sink (X4)

Since the operator decision of 2026-11-21 ([semgrep-runs-nightly.md](semgrep-runs-nightly.md))
Semgrep does not judge pull requests at all: the nightly sink is where it runs,
and where every Semgrep finding a repository carries goes.

| Piece | Where |
|---|---|
| Workflow | [`.github/workflows/nightly-sink.yml`](../.github/workflows/nightly-sink.yml), generated by `python3 tools/nightly_sink.py render` from [`central-semgrep.yml`](../.github/workflows/central-semgrep.yml)'s steps |
| Tool | [`tools/nightly_sink.py`](../tools/nightly_sink.py): `plan`, `render [--check]`, `publish`, `report` |
| Repositories | [`.l9/promotion-canary.json`](../.l9/promotion-canary.json) (entries with `nightly` not `false`), each at its main head |
| Waivers | Core's central finding-waiver ledger, [`.github/actions/resolve-governance/finding-waivers.yaml`](../.github/actions/resolve-governance/finding-waivers.yaml) (`l9.finding-waivers/v1`), as staged for the scan by resolve-governance |
| Tests | [`tests/tools/test_nightly_sink.py`](../tests/tools/test_nightly_sink.py) |

## What a night does

1. **Scan.** central-semgrep.yml's steps run verbatim apart from the target
   identity, as a `nightly` event on a clean checkout: the whole tree, no
   baseline, every planned instance (languages and the consumer rulepack). No
   repository verification runs, and the scan's own enforcement step is not
   run, so a repository that is already red is still scanned and published.
   org-ci.yml's `Biome` check then runs on the whole tree, advisory
   ([biome-check.md](biome-check.md)); its SARIF is one more category,
   `l9-central/biome/`. org-ci.yml's `gitleaks` check's own scan step runs on
   the whole tree (`gitleaks dir`), its findings written as SARIF, category
   `l9-central/gitleaks/`, and counted like Semgrep's. org-ci.yml's `CodeQL`
   check's language, install and analyze steps run on the whole tree (no
   base), one SARIF per language as `l9-central/codeql-<language>/`, counted;
   a CodeQL upload that code scanning refuses (CodeQL default setup still on)
   fails the night by name after every other category is published
   ([codeql-check.md](codeql-check.md)). org-ci.yml's `actionlint` check runs
   on every workflow, findings as `l9-central/actionlint/`, counted
   ([actionlint-check.md](actionlint-check.md)). bandit runs here and nowhere else (it is not a
   pull-request check; [security-checks.md](security-checks.md)): the whole
   tree, every severity, tests excluded at any depth, SARIF as category
   `l9-central/bandit/`, and the full JSON report kept as the run's
   `bandit-<repository>` artifact.
2. **Project.** The primary language's SARIF comes from the analyze steps; every
   other instance bundle (secondary languages, the declared consumer rulepack)
   is projected by the same SDK (`bundle project-sarif`). One file per instance.
3. **Publish.** Each file is uploaded to the scanned repository's code scanning
   with `automationDetails.id` `l9-central/<instance>/`, one category per
   instance, and the run waits for processing to finish. Code scanning is the
   system of record: alerts deduplicate across nights and close when fixed. A
   category that still has open alerts but no instance tonight (a dropped
   language or consumer rulepack) gets an empty analysis, so its alerts close.
4. **Report.** One issue per repository, "Nightly findings (Core central
   scan)", is created once and updated in place. It names the CODEOWNERS owner
   and lists new, fixed and still-open alerts against the previous night, with
   links. The previous night is the snapshot the issue carries.
5. **Dependency audit.** org-ci.yml's `pip-audit` check's own detection,
   Python and pip-audit steps are inlined into the sink job by the renderer (not copied by hand;
   `render --check` fails when they drift). As a nightly event the step audits
   the full resolved lock: `uv export --frozen --all-packages
   --no-emit-workspace --no-hashes --all-groups --all-extras` (each selection
   on its own when `[tool.uv].conflicts` is declared), else `requirements.txt`,
   with Core's pinned pip-audit, and writes a JSON report to the step's
   `PIP_AUDIT_REPORT` path. The issue gets a pip-audit section:
   packages audited, known vulnerabilities with advisory links and fixed
   versions, new and fixed against the previous night. A job-summary line per
   repository records the outcome and the package count.
6. **Ratchet.** Per tool, the open count may not rise night over night:
   Semgrep alerts in code scanning, and known vulnerabilities from pip-audit.
   Advisory tools (Biome, bandit) are listed in the issue and never counted.
   An incomplete audit (no lock, an export that fails, no report) also fails
   the night; an unknown set is not an empty one. Findings that a live entry
   of the central finding-waiver ledger matches are listed as waived and not
   counted; this is the same ledger pull-request gating reads, and there is no
   second one. A Semgrep finding matches by repository, provider, rule, path
   and fingerprint; a known vulnerability by provider `pip-audit`, the
   vulnerability id as the rule, the audited lock (`uv.lock` or
   `requirements.txt`) as the path, and the fingerprint
   `sha256("pip-audit\n<package>\n<version>\n<id>")`
   (`tools/nightly_sink.py dependency_fingerprint`). An entry past its expiry
   stops excluding its finding, so the count rises. A rise is commented on the
   issue and fails the run, and the issue keeps the last accepted night as the
   bar, so a re-run cannot clear it. The first night sets the baseline.

## Token

The l9-nightly-dispatch App (`vars.L9_NIGHTLY_APP_ID`,
`secrets.L9_NIGHTLY_APP_PRIVATE_KEY`), minted per repository with
`security-events: write`, `issues: write` and `contents: read`. Minting fails
when the installation lacks a permission or the repository. No PAT.

## Running it

Scheduled daily at 08:47 UTC. `workflow_dispatch` with `repository` set to one
declared `owner/name` runs that repository alone.
