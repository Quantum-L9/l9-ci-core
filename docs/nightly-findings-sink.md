# Nightly findings sink (X4)

Pull requests are judged on the findings they bring in (CENTRAL-DIFF, row 23).
The findings a repository already carries go to the nightly sink.

| Piece | Where |
|---|---|
| Workflow | [`.github/workflows/nightly-sink.yml`](../.github/workflows/nightly-sink.yml), generated by `python3 tools/nightly_sink.py render` from org-ci.yml's `analyze` steps |
| Tool | [`tools/nightly_sink.py`](../tools/nightly_sink.py): `plan`, `render [--check]`, `publish`, `report` |
| Repositories | [`.l9/promotion-canary.json`](../.l9/promotion-canary.json), each at its main head |
| Waivers | Core's central finding-waiver ledger, [`.github/actions/resolve-governance/finding-waivers.yaml`](../.github/actions/resolve-governance/finding-waivers.yaml) (`l9.finding-waivers/v1`), as staged for the scan by resolve-governance |
| Tests | [`tests/tools/test_nightly_sink.py`](../tests/tools/test_nightly_sink.py) |

## What a night does

1. **Scan.** org-ci.yml's analyze steps run verbatim apart from the target
   identity, as a `nightly` event: the whole tree, no baseline. The steps from
   "Enforce repository verification" on are not run, and the Biome check runs
   advisory, so a repository that is already red is still scanned and
   published.
2. **Project.** The primary language's SARIF comes from the analyze steps; every
   other instance bundle (secondary languages, the declared consumer rulepack)
   is projected by the same SDK (`bundle project-sarif`). One file per instance.
3. **Publish.** Each file is uploaded to the scanned repository's code scanning
   with `automationDetails.id` `l9-central/<instance>/`, one category per
   instance, and the run waits for processing to finish. Code scanning is the
   system of record: alerts deduplicate across nights and close when fixed. A
   category that still has open alerts but no instance tonight (a dropped
   language or consumer rulepack) gets an empty analysis, so its alerts close.
4. **Report.** One issue per repository, "Nightly findings (Core central
   scan)", is created once and updated in place. It names the CODEOWNERS owner
   and lists new, fixed and still-open alerts against the previous night, with
   links. The previous night is the snapshot the issue carries.
5. **Ratchet.** The open count may not rise night over night. Findings that a
   live entry of the central finding-waiver ledger matches by repository,
   provider, rule, path and fingerprint are listed as waived and not counted;
   this is the same ledger pull-request gating reads, and there is no second
   one. An entry past its expiry stops excluding its finding, so the count
   rises. A rise is commented on the issue and fails the run, and the issue
   keeps the last accepted night as the bar, so a re-run cannot clear it. The
   first night sets the baseline.

## Token

The l9-nightly-dispatch App (`vars.L9_NIGHTLY_APP_ID`,
`secrets.L9_NIGHTLY_APP_PRIVATE_KEY`), minted per repository with
`security-events: write`, `issues: write` and `contents: read`. Minting fails
when the installation lacks a permission or the repository. No PAT.

## Running it

Scheduled daily at 08:47 UTC. `workflow_dispatch` with `repository` set to one
declared `owner/name` runs that repository alone.
